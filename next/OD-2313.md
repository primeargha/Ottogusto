# OD-2313: Font migration to self-hosted TTF (next/font/local)

## 1. Font migration — `next/font/google` → `next/font/local`

- Removed `next/font/google` imports (`Anton`, `Inter`, `Overpass`, `Oswald`, `Public_Sans`, `Overpass_Mono`, `Chivo_Mono`) from `app/layout.tsx`.
- Replaced with `next/font/local`, pointing at self-hosted TTFs under `app/fonts/{inter,ottogusto,qverde}/`.
- Uses the exact same per-weight TTF files Google Fonts previously served (not the raw/unhinted GitHub source) — typography is pixel-identical to before.
- Removed the external Google Fonts loader block from `app/layout.tsx`:
  - `<link rel="preload" as="style" href="fonts.googleapis.com/css2?...">`
  - the idle-deferred `<script>` that injected the stylesheet
  - the `<noscript>` fallback `<link rel="stylesheet">`
- Removed the now-unneeded `fonts.googleapis.com` / `fonts.gstatic.com` `<link rel="preconnect">` hints.
- No more external Google Fonts CDN request at all — everything is served from the app's own origin.
- Moved the `--font-*` CSS variable `className` onto `<html>` so it's an ancestor of the `:root { --font-family-display: var(--font-anton), ... }` rule in the injected typography stylesheet. CSS custom properties resolve at the element where they're _declared_, not where they're inherited — this was required for `var()` to resolve correctly instead of computing to an invalid empty value.

## 2. CLS / layout-shift impact

- `next/font/local` auto-generates metric-matched fallback `@font-face` rules per font (`ascent-override`, `descent-override`, `line-gap-override`, `size-adjust`), tuned to each font's exact metrics — confirmed present in the build output for all 7 fonts.
- This is the same anti-CLS mechanism `next/font/google` already provided: the browser renders text in a size-matched local fallback immediately, then swaps to the real TTF with little to no layout shift.
- Removes the old _second_ font-loading path (the idle-deferred external Google Fonts stylesheet injection). That path was un-metriced and fired after first paint — the more likely real-world CLS contributor — and is now eliminated entirely.
- Net effect: reduces CLS risk versus the pre-migration setup. Confirmed at the code/build level (fallback metrics present, external path removed); not yet confirmed with a live before/after Lighthouse score.

## 3. Bug found & fixed — Oswald/Anton not rendering on mobile

- **Root cause**: `hooks/useThemeConfig.ts`'s `flattenObjectToCSSVars` / `applyThemeToDocument` walked the entire theme config — including `Font.Family.*` — and wrote raw, unmapped font names (e.g. `"Oswald"`) as **inline** `--font-family-*` styles on `<html>`. Inline styles always win over stylesheet rules, so this overrode the correctly-mapped `var(--font-oswald), sans-serif` value.
- Previously masked by the external Google Fonts stylesheet, which registered `Oswald`/`Anton` as real, resolvable bare-name font families. Once that stylesheet was removed, the bare name resolved to nothing and the browser fell back to generic sans-serif.
- Only manifested on **mobile**: the server always renders desktop typography by default, so `applyThemeToDocument` only ran (and corrupted the variables) once the client detected a mobile viewport and changed device state.
- **Fix**: `flattenObjectToCSSVars` now skips `Font.Family.*` entirely, leaving those CSS variables solely owned by `TypographyProvider`'s correctly-mapped stylesheet output. (`hooks/useThemeConfig.ts`)

## 4. Unrelated fix — Storybook "Cannot find module './tailwind.css'"

- Next.js's own ambient types only declare `*.module.css` (CSS Modules), not plain `*.css` — no ambient declaration existed anywhere in the repo for side-effect CSS imports like `.storybook/preview.tsx`'s `import "./tailwind.css"`.
- Added `types/css.d.ts` with `declare module "*.css";` so plain CSS imports resolve consistently across editors/TS servers.
