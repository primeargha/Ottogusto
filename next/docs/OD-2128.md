# OD-2128: Mobile CLS Fix (Homepage + Product Details Page)

## Problem

PageSpeed Insights field data (real 28-day Chrome UX Report) showed the homepage (`/en-BE`) failing Core Web Vitals on mobile with CLS 0.3, while desktop passed and the single-run lab test showed CLS 0.007. The lab test passed because it's one fast, unauthenticated run that never exercises the hydration-timing gaps real mobile users hit.

Root cause shape, in every case: content/styling that's correct in the server-rendered HTML changes again right after JS hydrates. Mobile is hit harder because (a) `useMedia` always assumes desktop on first render regardless of real device, so mobile visitors specifically get a layout correction, and (b) slower mobile networks widen the visible gap between first paint and that correction.

## Changes

### 1. Header logo — CSS-only swap

`screens/landing/header-row.tsx`

The logo used `isMobile ? mobileImg : desktopImg`, where `isMobile` comes from `useMedia` and defaults to `false` (desktop) until a `useEffect` runs. Mobile visitors briefly saw the desktop logo before it flipped.

Fixed by rendering both images and toggling visibility with Tailwind (`gtsm:hidden` / `gtsm:block`), so the correct logo is decided by CSS at first paint — no JS flip.

### 2. `getClientFeatureFlag` — SSR/CSR mismatch

`utils/theme-utils.ts`

The function derived locale from `window.location.pathname`, which doesn't exist during SSR. Result: it always returned `false` on the server and could flip to a different value on the client after mount — causing any feature-flagged UI driven by it to pop in/out post-hydration.

Fixed by preferring an explicit `languageCountrySegment` argument (e.g. from `useParams()`, available identically on server and client) over `window.location.pathname`. Backward compatible — callers that don't pass the segment keep the old `window`-based behavior.

### 3. Header right-section — removed `onClient` gate

`screens/landing/header-row.tsx`

The garage button, login/user menu, and language block were wrapped in `{onClient && (...)}`, so they didn't exist in the DOM until after mount, then popped in and shifted the cart icon/menu position.

- Removed the `onClient` gate for this block entirely — it now renders from first paint.
- Passed `languageCountrySegment` into the `getClientFeatureFlag` calls in this block (see #2).
- Converted the language block's `!isMobile &&` visibility check (JS-driven, same hydration-flip problem as #1) to a CSS class (`hidden gtsm:block`).

### 4. Hero/saved-cars carousel — CSS-only sizing + tighter image `sizes`

`screens/landing/LandingSavedcarsContainer2.tsx`

The carousel's container height was chosen via `!isMobile ? "gtsm:h-[265px]..." : "max-h-[180px]..."`, the same `useMedia`-driven flip as #1 — and the `fill` image inside it used `sizes="100vw"`, which is imprecise and made the late-loading image more likely to contribute to a shift when the container itself was still resizing.

- Replaced the JS ternary with unconditional Tailwind breakpoint classes (`base:`/`gtsm:`/`gtlg:`), matching the pattern already used in `header-row-skeleton.tsx`.
- Tightened `sizes` to `"(max-width: 639px) 100vw, 736px"`, mirroring the existing pattern in `heroCard2.tsx`.

### 5. `PreviousSearchClientContainer` — same SSR-safe feature-flag fix

`screens/landing/previous-search-client-container.tsx`

Had the identical `getClientFeatureFlag` mismatch from #2 (`home_previous_search_feature_flag`, `show_left_nav_flag`). Fixed the same way, passing `languageCountrySegment` derived from `useParams()`.

## Investigated, not changed

- **`screens/landing/reviews/index.tsx`** — has a `mounted` gate, but its container already reserves the full height before content mounts. Confirmed this does not contribute to CLS; no change needed.
- **`screens/landing/previous-search-carousel.tsx`** — has its own internal `typeof window !== "undefined" && window.innerWidth < 768` render-time branch (~line 593) that renders entirely different JSX for mobile vs desktop. This is a separate, deeper SSR/CSR mismatch from the ones fixed here. Not fixed in this pass — needs more investigation into intended behavior before a safe fix can be made. Flagged as a follow-up.
- **`PreviousSearchClientContainer`'s auth-gated mount** — originally suspected to need a reserved-space skeleton while `isAuthenticated` resolves. Investigation showed `useAuthStore`'s `persist` middleware rehydrates synchronously from localStorage (no `onRehydrateStorage` delay), and `RedirectManager`'s API call only fires for the _active_ login-button flow, not silent session restoration on page load — so there may not be a genuine multi-second pending window for returning users. Implementing a guessed-height skeleton risked introducing a _new_ flash for guest users. Left as-is pending further investigation; only the feature-flag mismatch (#5) was fixed here.

## Verification (Homepage)

- `npx tsc --noEmit` — clean, no type errors.
- Started the dev server and used Playwright (headless Chrome) to load the homepage at a 375px mobile viewport, dismiss the country/language selection modal, and measure real `layout-shift` Performance Observer entries.
- Result: CLS measured **0.003–0.02** locally (well under Google's "good" threshold of 0.1), with header, logo, and carousel all rendering correctly in screenshots.
- Note: local measurement is on a fast loopback connection: it confirms the structural hydration-flip causes are gone, but the actual field CLS number will only be confirmed once the next 28-day Chrome UX Report window updates after deploy.

## Part 2: Product Details Page (PDP)

### Problem

PageSpeed Insights mobile reports for PDP URLs (e.g. `/en-BE/car-parts/volvo/...`) showed the same class of bug as the homepage, dominated by one element: `id="scrollableDiv"`, content starting "Manufacturer ... OE Reference ... EAN ... Guaranteed fitment...", scoring **0.135** and **0.107** layout-shift in two separate PSI runs — roughly 40x bigger than every other contributor on the page (web fonts, a small "Volvo - timing" block at 0.001–0.002, and a one-time country/language modal at 0.003 for first-time visitors only).

### Root cause

`screens/productdetails/productfulldescription.tsx` had the exact same bug pattern as the homepage: JS-computed `isMobile` (from `useMedia`, defaults to `false`/desktop on first render regardless of the real device) and a local `isMounted` flag (set `true` in a `useEffect`, so always `false` at first paint) decided _which_ manufacturer/OE-reference/EAN/Package-Dimensions info boxes rendered:

1. **EAN box** — visibility was `isMobile ? "hidden" : "flex"`. Since `isMobile` starts `false` for everyone, this box was visible at first paint even on mobile, then hidden once `useMedia` resolved — a hide-after-paint shift.
2. **EAN-vs-Dimensions ternary** — `isMounted && isMobile ? <EAN box> : <Dimensions box>`. Since `isMounted` starts `false`, the Dimensions box always rendered first (even on mobile), then swapped to the EAN box post-hydration. This was the main content-swap and the dominant contributor to the 0.135/0.107 score.
3. **Mobile-only Dimensions box** — gated by `isMounted && isMobile &&`, so it didn't exist in the DOM at all until after hydration, then popped in alongside the swap above.

### Fix

Same proven approach as the homepage fix: stop deciding visibility in JS, let Tailwind's responsive classes (`base:`/`gtsm:`/`gtlg:`, already used throughout this file) decide it instead, so the correct boxes are visible from first paint with no post-hydration swap.

In `screens/productdetails/productfulldescription.tsx`:

- EAN box: `${isMobile ? "hidden" : "flex"}` → static `hidden gtsm:flex`.
- The `isMounted && isMobile ? EAN : Dimensions` ternary was split into two independently-rendered boxes, each gated only by data availability (not device), with CSS deciding which is visible: the EAN box got `gtsm:hidden` (mobile-only), the Dimensions box got `hidden gtsm:flex` (desktop/tablet-only).
- The mobile-only Dimensions box's `isMounted && isMobile &&` guard was removed, keeping only the data-availability check — it already carried `base:flex gtsm:hidden gtlg:hidden` in its className, so CSS alone now decides visibility.
- Removed `isMobile` and `isMounted` (plus the `useEffect` that set it) from the component — both became fully unused once their only call sites were converted to CSS, confirmed via `grep` before removal.

This is a pure refactor of _how_ visibility is decided (CSS vs. JS) — the final rendered DOM for a fully-hydrated client is unchanged, so there's no visual regression once hydrated; mobile users now see the correct boxes immediately instead of after a swap.

### Investigated, not changed

- **Header logo (`components/og-components/OGLanguageSelectionModel.tsx:101-112`) and cart icon (`components/og-components/OGButton.tsx:259-264`)** — Lighthouse's "unsized image" diagnostic flags these because a fixed-size wrapper `Box` (`h-5 w-5` / `w-[180px]`) constrains an `Image` with different explicit width/height. The wrapper size is static (not JS-computed), so it does not actually shift layout — a Lighthouse heuristic false-flag, not a CLS contributor.
- **Country/Language selection modal** — its ~0.003 score is the one-time, unavoidable shift of a modal appearing for first-time visitors with no saved locale. Two orders of magnitude smaller than the `scrollableDiv` issue; not worth changing.
- **"Volvo - timing..." block** (~0.001–0.002) — too small relative to the dominant 0.135/0.107 culprit to be worth the risk; not investigated further.

### Follow-up: `matchingCarsSection` mount gate

After the fix above was committed (`5dd2dc8f`), a fresh PageSpeed run against the **live production site** (not yet running the new commit) still showed `scrollableDiv` shifts — expected, since that fix hadn't deployed yet — plus a second, separate shift event (~0.080) also attributed to `scrollableDiv`.

Investigation found a second, independent mount-gate bug in `screens/productdetails/productdetails.tsx`: `{isMounted && matchingCarsSection}` (line 283) wrapped the "matching/compatible cars" section in a _local_ `isMounted` flag — a second, separate `isMounted` from the one already removed from `productfulldescription.tsx`. This section is itself a `dynamic(..., { ssr: false, loading: () => <ProductDetailsCompatibilityLoading /> })` import (`app/(public)/[language-country]/car-parts/[partname]/[partid]/page.tsx`), which already has its own correctly-sized loading skeleton (`ProductDetailsPageLoading.tsx`). The extra `isMounted &&` wrapper in `productdetails.tsx` was redundant on top of that — it delayed even _mounting_ the dynamic import (and therefore its own skeleton) by one additional render cycle, during which nothing at all rendered (not even a skeleton), then the whole section popped in.

**Fix:** removed the redundant `isMounted` gate and the now-unused `isMounted`/`setIsMounted` state from `productdetails.tsx` — the dynamic import's own `ssr:false` + `loading` skeleton already handles this correctly without it.

### Investigated, inconclusive — flagged for the user

The price/stock/delivery card (`screens/productdetails/productprice.tsx`) has two pieces of content that arrive from a client-only React Query call with no SSR prefetch and intentionally **no caching** (`gcTime: 0, staleTime: 0` in `hooks/productdetails.ts` — likely deliberate, for stock-accuracy reasons):

- A stock-count suffix (`(N)`) that only renders once `useGetInstockInformationQuery` resolves.
- Delivery-time text that shows a hardcoded `"Not available"` fallback before the query resolves, then swaps to the real delivery estimate.

This is a plausible contributor to a PDP shift, but **not confirmed** — these are single-line flex rows (`flex-row`, no `flex-wrap`), so text-length changes inside them don't obviously force a wrap/height change, and this sandbox has no network access to load real product data and measure it directly. Two ways to fix this exist, with different risk profiles: (a) low-risk — reserve a fixed-width placeholder for the count/delivery text so its arrival never changes element size, or (b) higher-effort but more thorough — prefetch this data server-side and hydrate it (a pattern not currently used anywhere in this codebase, so it would be a new architectural addition). Left unimplemented pending the user's input, since the existing `gcTime:0`/`staleTime:0` setting suggests stock freshness may be business-critical and any caching-adjacent change deserves explicit confirmation first.

### Verification (PDP)

- `npx tsc --noEmit` — clean, no type errors.
- `grep` confirmed `isMobile`/`isMounted` had no remaining usages in the file before removing them.
- Started the dev server and used Playwright (headless Chrome) to load a PDP route at a 375px mobile viewport — no console errors related to the changed file, page rendered without crashing.
- **Limitation:** this sandbox has no network access to the live product API, so a real product's manufacturer/OE-reference/EAN/Dimensions boxes could not be visually screenshotted end-to-end here. The fix is a mechanical, scoped CSS-class refactor (same pattern already verified effective on the homepage) with no change to final rendered output — recommend a final visual check against a real PDP URL (mobile + desktop) in an environment with API access before/after deploy.

## Part 3: PDP — CompatibleCarList, hero image, recently-viewed, breadcrumb (follow-up session)

A later PageSpeed/CLS pass on the PDP, after Parts 1–2 above had already shipped, found the score still wasn't at 0. This part covers that follow-up investigation and fixes.

### 1. Hero image — duplicate/conflicting Tailwind class

`screens/productdetails/ProductMainImage.tsx`, `screens/productdetails/productimgcarousal.tsx`

Both had `className={\`h-[240px] h-auto max-h-[241px] w-full ... gtlg:h-auto\`}`— an unprefixed`h-auto`sitting alongside the unprefixed`h-[240px]`on the same element, so which one won depended on Tailwind's generated CSS order, not intentional cascade. **Fix:** removed the stray unprefixed`h-auto`, keeping `h-[240px] max-h-[241px] ... gtlg:h-auto`(the`gtlg:` override is intentional and stays).

### 2. `CompatibleCarList.tsx` — oversized/unbounded skeleton

`screens/productdetails/components/CompatibleCarList.tsx`

The compatible-cars API can return anywhere from a couple of cars to hundreds for a single brand (accordions open all-expanded by default), so the real height is unbounded and unknowable up front — no fixed skeleton height can match every part.

- Iterated the skeleton size down from an original `min-h-[100vh] × 4 cards` (reserved up to ~4 viewport-heights, causing a huge _shrink_ shift when real data loaded) to a smaller, more realistic `2 cards × min-h-[260px] (mobile) / 268px (gtsm+)` estimate.
- **Final fix, since a static guess can never converge to 0 CLS for unbounded content:** the real rendered height is now measured (`getBoundingClientRect().height`) after data loads and cached in `sessionStorage`, keyed by part ID + mobile/desktop viewport bucket (`utils/safeStorage.ts`'s `createSafeStorage` was exported for reuse here). The loading skeleton reads this cached value first and uses it as an exact `min-height` override; only a part's very first-ever view (no cache yet) falls back to the static per-card estimate. Every repeat view reserves the exact right height.
- A separate attempt to cap each brand's item list to a fixed count with a "Show N more" reveal (in `productfaqcard.tsx`) was tried and then **reverted by the user** — left as unclamped/original; not to be re-attempted without asking.

### 3. Recently-viewed section — hydration gap

`stores/useRecentlyViewedProductStore.ts`, `screens/productdetails/productdetails.tsx`

`recentlyViewedProduct` starts as `[]` and the whole block (`Divider` + `Productfrequentlybought`) only rendered once `recentlyViewed.length > 0` — which is only known after zustand's `persist` middleware finishes async localStorage rehydration. For returning visitors (the ones who actually have items), the block popped in fully from nothing after mount.

**Fix:** added `useRecentlyViewedHydrated()` to the store (using persist's `hasHydrated()`/`onFinishHydration()`). `productdetails.tsx` now shows the existing `ProductfrequentlyboughtLoading` skeleton shape while hydration is pending, instead of rendering nothing — so the transition is skeleton→content, not nothing→content.

### 4. `productmatchingcars-client.tsx` — redundant `isMounted` gating

`compatibleSectionEnabled`, `useCarsApiPath`, and `savedCarFeatureFlag` were all gated behind a local `isMounted` flip (`useEffect` → `setIsMounted(true)`), forcing an extra client-only re-render/layout switch. Since this component only ever mounts via a `dynamic(..., { ssr: false })` import, `window` is already available on its very first render — the gating was pure boilerplate. **Fix:** removed `isMounted` entirely; the feature-flag functions are called directly on first render.

### 5. `OGBreadcrumb.tsx` — tooltip trigger sizing

The "product-details" active breadcrumb item wraps its label in `CustomTooltip` (an extra `inline-flex` trigger `Box`). Without constraints, that extra wrapper could push the item onto a 2nd line at some viewport widths (the `<ol>` is `flex-wrap`), growing the nav's height after hydration — the tooltip popover itself is a `position: fixed` portal to `document.body` and doesn't affect layout, so this was specifically about the trigger element. **Fix:** added `min-h-4 whitespace-nowrap max-w-full` to that `<li>` only (not the plain-text branch, to avoid changing wrap behavior for long category names on non-PDP pages). Also added a small `base:min-h-[36px] gtsm:min-h-0` safety margin on the `<nav>` itself for the rarer case of a very deep category path wrapping to 2 lines on mobile.

### Verification

`npx tsc --noEmit` and project ESLint clean on every file touched. Manual verification (mobile emulation, network-throttled repeat visits, long-fitment parts) recommended before deploy, same limitation as Part 2 — no live product API access in this sandbox.

`components/og-components/Typography.tsx`

## Part 7: Cookiebot consent banner — third-party layout shift

`styles/global.css`

PageSpeed flagged a large layout shift attributed to Cookiebot's cookie-consent dialog (`#CybotCookiebotDialog`). This banner is injected by a third-party script (loaded via GTM) well after first paint, and by default renders in normal document flow — so when it appears, it pushes all existing page content down, which is scored as a layout shift. Worse on mobile, where the banner takes up a much larger fraction of the viewport. Since it's third-party markup injected at runtime, there's no first-party placeholder to reserve space for it ahead of time.

**Fix:** added a CSS override forcing `#CybotCookiebotDialog { position: fixed !important; }`. This takes the dialog out of document flow entirely, so its arrival can no longer reflow anything below it — it still displays and still gates consent normally, it just overlays the page instead of pushing content down.

CSS-only change; no build/type-check impact expected.

## Part 8: `useMedia` — resolve in a layout effect, not a passive effect

`hooks/useMedia.ts`

Parts 1, 2, 4 and 6 above fixed individual call sites by removing their dependency on `isMobile` for layout decisions and moving that decision into CSS instead. But `useMedia` itself is used more broadly across the codebase (e.g. `OGProductcard` switches its entire "Card" vs "Mobile" shape based on it), and every one of those call sites had the same latent bug: `useMedia` resolved its `matchMedia` check inside a plain `useEffect`, which React runs as a **passive effect** — asynchronously, after the browser has already painted. So on mobile, the hook committed its SSR default (`false`, i.e. "desktop") for one full paint, then flipped to `true` and caused a reflow, even for components that had no other CLS bug of their own.

**Fix:** changed the internal `useEffect` to `useLayoutEffect` (via an `useIsomorphicLayoutEffect` helper that falls back to `useEffect` when `window` is undefined, since `useLayoutEffect` warns if it ever runs during SSR). `useLayoutEffect` fires synchronously after DOM mutations but **before** the browser paints, so the correct mobile/desktop value is committed in the very first paint instead of a paint-then-correct cycle. This is a fix at the shared-hook level, so it benefits every remaining `useMedia` consumer in the codebase (not just the ones explicitly listed in Parts 1–7), including layout-branching components like `OGProductcard` that weren't otherwise touched in this pass.

### Verification

`npx tsc --noEmit` clean.

## Part 9: PDP follow-up — closing the two "inconclusive" items from Part 2

After the Cookiebot fix (Part 7) is deployed and given time to reflect in a
full 28-day CrUX window, these two PDP items — left open in Part 2 as
"investigated, inconclusive" — are the next most likely remaining
contributors. Both fixed here without touching any data-fetching/caching
behavior.

### 1. `productprice.tsx` — reserved height for stock-count and delivery text

`screens/productdetails/productprice.tsx`

The stock-count `(N)` suffix and the delivery-time text both arrive from
`useGetInstockInformationQuery` (intentionally uncached — `gcTime: 0,
staleTime: 0` in `hooks/productdetails.ts`, presumably for stock-accuracy
reasons), swapping in after a no-count / `"Not available"` fallback.

**Fix:** rather than touching the caching (out of scope — the `gcTime`/`staleTime`
setting looks deliberate), reserved a defensive `min-h` on the two affected

- Availability row: `min-h-[20px]` added alongside the existing `h-auto`.
- Delivery row: `min-h-[40px]` on the outer row plus `min-h-[20px]
flex-wrap` on the inner label/value `Box`, sized to silently absorb a
  worst-case 2-line wrap (delivery text length varies meaningfully by locale
  and by which of "Not available" / a real delivery estimate / "TBD" is
  shown) instead of overflowing or reflowing surrounding content.

### 2. `CompatibleCarList.tsx` — global running-average fallback height

`screens/productdetails/components/CompatibleCarList.tsx`

The existing per-part `sessionStorage` height cache (Part 3 §2) already
gives repeat views of the same part an exact skeleton height. Only a part's
very first-ever view had no cache yet and fell back to a static, generic
2-card estimate that can under/over-shoot a real part's compatible-car-brand
count.

**Fix:** added a second, site-wide fallback — a `localStorage`-backed
(persists across sessions, unlike the per-part cache) exponential moving
average of real measured heights, tracked separately per mobile/desktop
bucket (`GLOBAL_HEIGHT_KEY_PREFIX`, `GLOBAL_HEIGHT_EMA_WEIGHT = 0.2`). Every
real data load updates both the per-part cache (unchanged) and this global
average. Lookup order for the skeleton's `minHeightPx` is now: per-part
cache → global running average → today's static per-card estimate as the
last resort. In practice this means only a user's literal first-ever
compatible-cars view on a given device falls back to the generic guess;
every subsequent view of _any_ part (not just a repeat view of the _same_
part) benefits from a real-world-informed height.

## Part 10: Homepage — `previous-search-carousel.tsx` structural hydration mismatch

`screens/landing/previous-search-carousel.tsx`

This was flagged in Part 1 as a deeper, unfixed bug: the `isPreviousSearch`
config picked between two **entirely different JSX trees** — a plain
native-scroll mobile list (no arrows, no drag JS) vs. a shared `transform`

- touch-drag + arrows desktop carousel — using a raw render-time check:

```js
if (typeof window !== "undefined" && window.innerWidth < 768 && config.isPreviousSearch) {
  return ( /* mobile tree */ );
}
// falls through to the shared/default tree (desktop)
```

`window` doesn't exist during SSR, so the server always emitted the desktop
tree regardless of device. On the client's very first render, mobile
visitors immediately evaluated this `true` — a genuine hydration mismatch
(server tree A, client wants tree B on the first pass), which is more
disruptive than the state-flips-after-mount pattern fixed elsewhere in this
doc: React discards/replaces the whole mismatched subtree — different
container element, different scroll mechanism entirely — rather than a
simple class/visibility toggle.

**Fix:** same established pattern as the header logo (Part 1 §1) and hero
carousel (Part 1 §4) — render **both** shapes unconditionally and let CSS
decide visibility, using the same 768px breakpoint (`md:`, already defined
in `tailwind.config.js`) the old JS check used:

- Mobile shape (native `overflow-x-scroll`, no arrows): wrapped in `block md:hidden`.
- Desktop shape (arrows + `transform`/touch-drag): wrapped in `hidden md:block`.

Both trees now mount in the initial HTML (server and client emit identical
markup), so there's no mismatch and no swap — the correct one is simply
visible from first paint. Trade-off: both DOM trees render (only one is
visually shown at a time), matching the same trade-off already accepted for
the header logo/hero carousel fixes.

**Also fixed in the same file:** `isDesktop` (used to gate arrow visibility)
was a plain `useState(true)` plus a manual `useEffect`/`resize`-listener
